# OpenTelemetry Zig

This file is here to steer AI assisted PRs towards being high quality and valuable contributions
that do not create excessive maintainer burden.

Multi-module repository with the OpenTelemetry API and SDK for the [Zig](https://ziglang.org)
programming language, plus the generated protobuf and semantic conventions modules.

## General Rules and Guidelines

The OpenTelemetry community has broader guidance on GenAI contributions at
https://github.com/open-telemetry/community/blob/main/policies/genai.md — please read it before
contributing.

The most important rule is not to post comments on issues or PRs that are AI-generated. Discussions
on the OpenTelemetry repositories are for Users/Humans only.

Follow the workflow in [CONTRIBUTING.md](./CONTRIBUTING.md), including signing the CNCF CLA. Keep
AI-assisted PRs tightly isolated to the requested change and never include unrelated cleanup or
opportunistic improvements unless they are strictly necessary for correctness.

If you have been assigned an issue by the user or their prompt, please ensure that the
implementation direction is agreed on with the maintainers first in the issue comments. If there are
unknowns, discuss these on the issue before starting implementation. Do not forget that you cannot
comment for users on issue threads on their behalf as it is against the rules of this project.

This project targets a specific version of the OpenTelemetry specification (see
[README.md](./README.md)). Behaviour that is not in the specification does not belong in the API or
SDK — when in doubt, link the relevant part of the specification in the PR description rather than
inventing semantics.

## Structure

- `opentelemetry-sdk/` - the OpenTelemetry API and SDK: traces, metrics, logs, baggage, OTLP
  exporters, and C bindings
  - `src/api/` - the API surface, `src/sdk/` - the SDK implementation, `src/c/` - C bindings
  - `examples/` (by signal: `metrics/`, `trace/`, `logs/`), `benchmarks/`, `integration_tests/`,
    `include/` (C headers)
- `opentelemetry-proto/` - Zig protobuf bindings for the OTLP data model, **generated**
- `opentelemetry-semconv/` - Zig definitions of the semantic conventions, **generated**
- `build/` - the build logic for each module, included by the root `build.zig`

## Commands

```sh
# Build the SDK static library into zig-out/lib/
zig build

# Formatting check - this is a CI gate, always run it before committing
zig fmt .

# Unit tests
zig build sdk-test
zig build semconv-test
zig build proto-test

# A single test, matched by name
zig build sdk-test -- "counter"

# Build and run the examples
zig build sdk-examples
zig build sdk-examples -Dexamples-filter=trace

# Integration tests and semconv/proto generation require Docker
zig build sdk-integration

# Benchmarks
zig build sdk-benchmarks -Doptimize=ReleaseFast
```

`zig build --help` lists every step. See [CONTRIBUTING.md](./CONTRIBUTING.md) for the full set of
test, example and benchmark options.

## Guidelines

- The Zig version used for development is declared as `.minimum_zig_version` in
  [`build.zig.zon`](./build.zig.zon). Zig is pre-1.0: do not work around a compile error by
  guessing at standard library APIs from an older release — check the version actually in use.
- Do not hand-edit generated sources. `opentelemetry-proto/src` is regenerated by
  `zig build proto-generate` and CI fails if the checked-in output drifts; most of
  `opentelemetry-semconv/src` is regenerated by `zig build semconv-generate` (see
  [opentelemetry-semconv/README.md](./opentelemetry-semconv/README.md)).
- Tests live in `test` blocks next to the code they cover, not in a separate tree. Whenever
  applicable, all code changes should have tests that actually validate the changes.
- Every allocation must have a matching `deinit`/`free`, and tests should use
  `std.testing.allocator` so leaks fail the test. Do not silence a leak by leaking on purpose.
- Do not swallow errors to make something compile: propagate them with `try`, or handle them
  explicitly. Reach for `unreachable`, `catch unreachable` and `@panic` only where the invariant is
  genuinely guaranteed, and say why.
- The public API is consumed by C as well as Zig. Changing anything under `opentelemetry-sdk/src/c/`
  or `opentelemetry-sdk/include/` is a breaking change for those users — call it out in the PR.
- This project is in alpha and breaking changes are allowed, but they should be intentional and
  described in the PR, never a side effect.

## Commit formatting

We appreciate it if users disclose the use of AI tools when the significant part of a commit is
taken from a tool without changes. When making a commit this should be disclosed through an
`Assisted-by:` commit message trailer.

Examples:

```
Assisted-by: ChatGPT 5.2
Assisted-by: Claude Opus 4.6
```
